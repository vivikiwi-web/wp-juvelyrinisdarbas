# Архитектура — предложение

Обязательные требования: [AGENTS.md](../AGENTS.md). Несогласованные решения: [decisions.md](decisions.md). Структура ниже ещё не реализована.

## Существующий слой

WordPress + Savoy + WooCommerce обеспечивают базовую страницу магазина, сетку и карточку изделия. WPBakery и `nm-custom-code` обеспечивают редактируемый hero и страницы. Начальная компоновка описана в [аудите](audit-2026-11-24.md).

Новые каталоги и пустые заготовки runtime-файлов заранее не создаём. Когда будет поручена реализация, можно использовать структуру:

```text
functions.php                    # подключение собственных модулей
inc/catalog.php                  # хуки каталога и запрет покупки
inc/product-fields.php           # администраторские настройки изделия
inc/inquiry/schema.php           # допустимые сценарии и параметры
inc/inquiry/validation.php       # серверная проверка и канонические данные
inc/inquiry/cf7.php              # интеграция с конкретной CF7-формой
inc/inquiry/storage.php          # только если согласовано хранение
template-parts/inquiry-drawer.php
assets/js/inquiry.js
assets/css/inquiry.css
```

Это ориентир, а не требование создать все файлы. Небольшие связанные части допустимо объединить. WooCommerce-шаблоны переопределяются только если нужное поведение нельзя получить хуками.

## Данные изделия

- `product`, `product_cat`, фото/галерея, SKU и подтверждённые характеристики — штатные сущности WooCommerce.
- Старый ID и источник импорта хранятся отдельно от названия. SKU сохраняет старый номер, если его уникальность и смысл подтверждены.
- Фактическое наличие готового варианта и разрешение индивидуального изготовления — разные признаки.
- Материал и цвет золота разделены. Для серебра поле цвета золота неприменимо.
- Реальная вариация готового изделия допустима при самостоятельном остатке/характеристиках. Желаемый размер, гравировка и другие пожелания сами по себе не требуют вариации.
- Допустимые параметры задаются схемой категории/изделия, а не произвольными полями из браузера.

## Поток запроса

1. Кнопка передаёт ID изделия. Панель получает разрешённые публичные данные и сценарии от сервера.
2. Клиент выбирает сценарий и параметры. Локальное состояние и восстановление зависят от согласованного решения.
3. CF7 принимает контакты и полезную нагрузку запроса. Интеграция ограничена конкретной формой, чтобы не менять остальные формы сайта.
4. До отправки сервер получает актуальное изделие через API WC, проверяет опубликованность, сценарий, вариант и параметры. Ошибки привязываются к форме и показываются по-литовски.
5. Название, SKU, ссылка и сведения для письма формируются по серверным данным. Если согласован архив, сохраняется проверенный снимок запроса с учётом защиты от повторов.
6. CF7 отправляет письмо. UI обрабатывает успех/ошибку; выбор очищается только после подтверждённого результата соответствующего запроса.

Не запускать отдельное создание заказа из браузерного `wpcf7mailsent`, как в Bioresus. Если архив и письмо имеют разные результаты, нужна явная политика частичного успеха. AJAX/REST endpoint просмотра данных не должен отправлять письмо или резервировать изделие.

## Серверный запрет покупки

Savoy Catalog Mode можно использовать для оформления после разрешения настройки БД. Он скрывает в том числе наличие и стандартные действия, поэтому нужны собственные CTA и статус сценария.

В дочерней теме необходимо проверить и ограничить поддерживаемые текущей версией WC пути покупки: обычные формы/URL, WC AJAX, Store API, доступ к checkout и платёжным действиям. Не полагаться на CSS или один фильтр. Нельзя при этом ломать чтение каталога, административное редактирование и импорт.

## Хранение и безопасность

Собственное состояние отделено от покупательской корзины — рекомендация. На сервере важна проверка каждого запроса, а не доверие к сохранённому состоянию или nonce. Ограничиваются размеры данных, допустимые значения, файлы (если разрешены), частота отправок и повторные действия.

Контакты не помещаются в URL, публичное кеширование или браузерное долговременное хранилище. Если нужен архив, рекомендуется закрытый тип записи с административными правами; это отдельная реализация, не оплаченный/processing WC order.

Подробные проверки: [inquiry.md](workflows/inquiry.md).
