# Архитектура — предложение

Обязательные требования: [AGENTS.md](../AGENTS.md). Несогласованные решения: [decisions.md](decisions.md). Структура ниже ещё не реализована.

## Существующий слой

WordPress + Savoy + WooCommerce обеспечивают базовую страницу магазина, сетку и карточку изделия. WPBakery и `nm-custom-code` обеспечивают редактируемый hero и страницы. Начальная компоновка описана в [аудите](audit-2026-11-24.md).

Уточнение владельца от 2026-11-24: использовать дизайн штатной боковой панели Savoy, поставить CF7 внизу, сохранять запрос в WooCommerce-заказе без покупки. Предложение отдельного типа записей для запросов отменено. Цена для всех/части изделий остаётся открытой.

Новые каталоги и пустые заготовки runtime-файлов заранее не создаём. Когда будет поручена реализация, можно использовать структуру:

```text
functions.php                    # подключение собственных модулей
inc/catalog.php                  # хуки каталога и запрет покупки
inc/product-fields.php           # администраторские настройки изделия
inc/inquiry/schema.php           # допустимые сценарии и параметры
inc/inquiry/validation.php       # серверная проверка и канонические данные
inc/inquiry/cf7.php              # интеграция с конкретной CF7-формой
inc/inquiry/orders.php           # заказ-запрос, повторы, статус и ограничения
template-parts/woocommerce/cart-panel.php # если нужен override оболочки Savoy
woocommerce/cart/mini-cart.php    # только если хуков недостаточно для списка
assets/js/inquiry.js
assets/css/inquiry.css
```

Это ориентир, а не требование создать все файлы. Небольшие связанные части допустимо объединить. WooCommerce-шаблоны переопределяются только если нужное поведение нельзя получить хуками.

## Повторное использование панели Savoy

В установленной Savoy `nm_footer_includes()` вызывает `get_template_part('template-parts/woocommerce/cart-panel')`, что допускает одноимённое переопределение в child theme. Сама оболочка вызывает `woocommerce_mini_cart()`; список и нижние действия находятся в `savoy/woocommerce/cart/mini-cart.php` (версия шаблона 11.2.2). Сначала используй подходящие хуки, копируй только необходимые шаблоны и фиксируй их исходную версию.

Сохраняются расположение, стили, открытие и закрытие Savoy; надписи переводятся на литовский, добавляются SKU/параметры и CF7 вместо покупательских действий. Точная светлая/тёмная тема панели отдельно не утверждена; скриншот не разрешает менять весь сайт.

`nm_get_cart_fragments()` заменяет целиком `div.widget_shopping_cart_content`. Рекомендуется разместить CF7 в оболочке вне этого фрагмента и проверить высоту/прокрутку панели. Иначе изменение количества или удаление изделия может сбросить введённые контакты и инициализацию CF7.

Savoy отключает штатную панель при `shop_catalog_mode=1`; глобальное включение Catalog Mode также скрывает цены. Для выбранного направления нужно точечно ограничить покупку, сохранить панель и предусмотреть выборочное отображение цен, а не включать этот режим без анализа.

Выбор механизма списка ещё не утверждён: штатная WC cart/session может упростить интеграцию с Savoy, но по умолчанию требует покупаемость и учитывает складские ограничения. Для запроса изготовления и изделия без цены нужны отдельные проверенные правила; не включать глобально покупаемость всех товаров.

## Данные изделия

- `product`, `product_cat`, фото/галерея, SKU и подтверждённые характеристики — штатные сущности WooCommerce.
- Старый ID и источник импорта хранятся отдельно от названия. SKU сохраняет старый номер, если его уникальность и смысл подтверждены.
- Фактическое наличие готового варианта и разрешение индивидуального изготовления — разные признаки.
- Материал и цвет золота разделены. Для серебра поле цвета золота неприменимо.
- Реальная вариация готового изделия допустима при самостоятельном остатке/характеристиках. Желаемый размер, гравировка и другие пожелания сами по себе не требуют вариации.
- Допустимые параметры задаются схемой категории/изделия, а не произвольными полями из браузера.

## Поток запроса

1. Кнопка передаёт ID изделия. Панель получает разрешённые публичные данные и сценарии от сервера.
2. Клиент выбирает сценарий и параметры. Локальное состояние и восстановление зависят от согласованного решения.
3. CF7 принимает контакты и полезную нагрузку запроса. Интеграция ограничена конкретной формой, чтобы не менять остальные формы сайта.
4. До отправки сервер получает актуальное изделие через API WC, проверяет опубликованность, сценарий, вариант и параметры. Ошибки привязываются к форме и показываются по-литовски.
5. Название, SKU, ссылка, известная цена и параметры формируются по серверным данным. Сервер создаёт один заказ-запрос через WC CRUD с защитой от повторов, сохраняет сценарий и пожелания в метаданных позиций и контакты клиента. Неизвестная цена явно отмечается в данных запроса: техническое нулевое значение суммы не означает бесплатное изделие.
6. CF7 отправляет уведомление со ссылкой/номером созданного запроса. UI обрабатывает успех/ошибку; выбор очищается только после подтверждённого результата соответствующего запроса. Частичная ошибка письма не должна создавать второй заказ при повторе.

Не запускать отдельное создание заказа из браузерного `wpcf7mailsent`, как в Bioresus. Сохранение и отправка координируются на сервере; точная политика частичного успеха ещё требует решения. AJAX/REST endpoint просмотра данных не должен отправлять письмо или резервировать изделие.

## Серверный запрет покупки

Catalog Mode нельзя включать автоматически: он скрывает цены, наличие и отключает штатную панель. Для сохранения панели и возможных выборочных цен нужны точечные изменения через child theme.

В дочерней теме необходимо проверить и ограничить поддерживаемые текущей версией WC пути покупки: обычные формы/URL, WC AJAX, Store API, checkout, order-pay и платёжные ссылки заказов-запросов. Если WC cart используется для списка, разрешённое добавление в запрос должно продолжать работать при закрытой оплате. Не полагаться на CSS или один фильтр. Нельзя ломать чтение каталога, административное редактирование и импорт.

## Хранение и безопасность

На сервере важна проверка каждого запроса, а не доверие к сохранённому состоянию или nonce. Ограничиваются размеры данных, допустимые значения, файлы (если разрешены), частота отправок и повторные действия. Список и способ восстановления ещё требуют выбора.

Контакты не помещаются в URL, публичное кеширование или браузерное долговременное хранилище. Заказы-запросы хранятся через WC CRUD с поддержкой HPOS, а не прямой записью в `wp_posts`. Рекомендуется отдельный статус `Užklausa`, а не `processing`/`on-hold`, связанные в установленной WC со снижением остатков. Заказ-запрос не вызывает `payment_complete`, не имеет даты оплаты, не резервирует и не списывает остатки; стандартные платёжные письма/ссылки и попадание в показатели продаж нужно проверить и ограничить для помеченных запросов. Жизненный цикл и правила ручной смены статусов ещё не определены.

Подробные проверки: [inquiry.md](workflows/inquiry.md).
